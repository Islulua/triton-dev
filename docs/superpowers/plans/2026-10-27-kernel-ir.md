# Kernel / IR Implementation Plan

> Execute inline with test-driven development. User authorized implementation after the design discussion; leave changes uncommitted for review.

**Goal:** Integrate source editing, compilation, stage selection, multiple linked IR panels and trace import into the existing triton-dev web app without changing Triton source.

**Architecture:** Vendor the BSD-licensed TritonParse location parser at a pinned revision behind a normalized document model. A registered compiler adapter runs in a separately configured sandbox launcher; platform SQL tasks persist state and results. Monaco editors are bundled locally. Imported and illustrative results stay explicitly distinct from actual compilation.

**Tech Stack:** Python, existing FastAPI/SQLAlchemy task platform, React/Vite, Monaco.

**Spec:** User-approved conversation: native integration in the existing website; major IR stages first; no changes to Triton internals.

## Constraints
- Preserve existing navigation, UI tokens, sessions, queue ownership, API error envelope and Sites packaging.
- Do not launch edited Python in the API process or grant it service credentials. Compilation requires an administrator-registered isolation launcher; missing toolchains return unavailable.
- Freeze source/configuration per compilation. Edited source invalidates mapping; old requests must not replace newer results.
- Map by normalized exact source identity and compiler locations, including inline callsites. Never invent missing mappings.
- Do not commit, push or change SDK/compiler repositories.

## Review focus
- Out-of-order responses and source edits while compiling.
- Same basename in different source directories; invalid/out-of-range imported mappings.
- Large or malformed compressed trace; no filesystem reads from trace paths.
- Cross-workspace access and cancellation of queued/active compilation.
- Local-only editor assets and production CSP, detached windows, model disposal.
